# PROJECT: SHAMAN — SINGLE-PLAYER GOD-GAME

## ROLE

You are the lead gameplay programmer working under a human project manager.

The goal is to create a single-player game inspired mechanically by Populous: The Beginning, but presented with a substantially more realistic, immersive, third-person fantasy aesthetic comparable to modern open-world RPGs.

The human project manager will provide design decisions and priorities. Do not independently redesign core mechanics unless explicitly asked.

Prioritize:

1. Playability
2. Faithful systemic gameplay
3. Strong game feel
4. Performance
5. Modularity
6. Easy iteration
7. Visual fidelity

Do NOT attempt to build the entire game simultaneously.

Build the game as a series of independently testable systems.

---

# 1. CORE DESIGN PHILOSOPHY

The player is the Shaman.

The Shaman is the primary hero, combatant, spellcaster, explorer, and strategic decision-maker.

The player’s tribe exists to support the Shaman.

The game should feel like:

> “I am personally walking through the world as the Shaman while simultaneously controlling an entire tribe.”

The player should NOT feel like an RTS camera controlling an army.

The player should NOT need complicated RTS-style micromanagement.

The Shaman should remain the star.

---

# 2. CORE GAME LOOP

The fundamental loop is:

EXPLORE
→ DISCOVER RESOURCES
→ ESTABLISH SETTLEMENT
→ GROW TRIBE
→ LEARN SPELLS/TECHNOLOGY
→ CONVERT/DEFEAT NEIGHBORING TRIBES
→ EXPAND
→ DEFEND AGAINST RAIDS
→ EXPLORE NEW BIOMES
→ DEFEAT STRONGER SHAMANS
→ ABSORB THEIR POWER
→ ADVANCE TO NEXT MAP
→ ASCEND

Every system should reinforce this loop.

Avoid adding systems merely because they are realistic.

## MANA

Mana regeneration is primarily determined by follower count.

More followers = faster mana regeneration.

This is a fundamental Populous-inspired mechanic.

Do not replace this with conventional RPG mana regeneration.

Use a configurable formula:

ManaRegen =
BaseRegen
× FollowerMultiplier
× TemporaryModifiers

Make all values data-driven.

Spells with no mana cost must still have availability restrictions, cooldowns, charges, or unlock conditions.

---

# 7. REINCARNATION

The Shaman cannot permanently die while a functioning reincarnation circle exists.

When killed:

1. Shaman dies.
2. Reincarnation timer begins.
3. Player respawns at the tribe’s reincarnation circle.
4. Reincarnation circle remains active.

Reincarnation time decreases as follower count increases.

Example:

RebirthTime =
BaseTime / FollowerModifier

Make the formula configurable.

Enemy reincarnation circles are invulnerable while their Shaman lives.

When an enemy Shaman is killed:

- Their reincarnation circle becomes vulnerable.
- Destroy/remove the circle.
- Enemy Shaman is permanently eliminated.
- Their mana/power becomes available to the player.
- Trigger Shaman-kill reward.

## RANGE AND MANA SCALE

The original spell information uses a 0–100 scale for range and mana.

For this project, preserve the relative balance while converting the values into practical world units and gameplay costs.

Use the following design rules:

- Range 0–15: close-range or emergency spells
- Range 16–35: short-to-medium combat spells
- Range 36–60: long-range tactical spells
- Range 61–100: strategic or map-wide spells
- Mana 0–15: early-game/basic spells
- Mana 16–35: common tactical spells
- Mana 36–60: powerful battlefield-control spells
- Mana 61–85: late-game destructive spells
- Mana 86–100: endgame spells

The original values should remain stored as reference balance values, but the actual project values must be editable through Data Assets or Data Tables.

# 11. SPELL DEFINITIONS

Implement the following spells as data-driven spell definitions.

The listed costs and ranges are starting balance targets for this project. Adjust them through playtesting while preserving their intended relative power.

## TAKA — BLAST

Status:

- Already implemented in Phase 1
- Starting spell
- Repeatable spell

Suggested project values:

- Range: 10
- Mana cost: 5
- Area: Small
- Damage: Low
- Knockback: High
- Ragdoll force: High
- Building damage: Low
- Friendly fire: Yes
- Terrain effect: None

Function:

Blast sends nearby followers, including friendly followers, flying into the air.

It is especially useful for:

- Disrupting enemy groups
- Pushing enemies into water
- Breaking enemy pursuit
- Creating space around the Shaman
- Knocking followers from boats or elevated positions

Blast should remain useful throughout the game because of its low mana cost, but its damage should remain modest.

## CONVERT

Suggested project values:

- Range: 100
- Mana cost: 5
- Area: Medium-to-large
- Damage: None
- Duration: Instant
- Friendly fire: No
- Target type: Wildmen
- Unlock tier: Early game

Function:

Convert is a non-offensive spell.

Wildmen caught within the area become Braves belonging to the player’s tribe.

The spell should:

- Affect only valid Wildmen
- Convert multiple Wildmen at once
- Ignore enemy followers unless a later upgrade explicitly allows it
- Provide clear visual feedback for affected targets
- Respect population-capacity rules
- Fail gracefully if no valid Wildmen are present

Because the range is high and the mana cost is low, the area of effect should be controlled to prevent excessive early population growth.

---

## SWARM

Suggested project values:

- Range: 30
- Mana cost: 50
- Area: Medium
- Duration: 12–18 seconds
- Damage: Very low
- Unlock tier: Mid game

Function:

Swarm creates an insect cloud that distracts affected followers.

Affected units should:

- Stop their current task
- Enter a panic state
- Attempt to flee from the swarm
- Interrupt preaching, construction, gathering, and combat
- Potentially jump from boats or elevated platforms if fleeing requires it
- Remain vulnerable to environmental hazards

Swarm should be primarily a disruption spell, not a direct damage spell.

Add safeguards so affected units do not become permanently trapped or run outside the playable area.

Suggested project values:

- Range: 30
- Mana cost: 25
- Area: Small-to-medium
- Duration: 20 seconds or until combat begins
- Unlock tier: Early game

Function:

Invisibility makes affected friendly followers invisible.

When an invisible follower:

- Begins attacking
- Takes direct combat action

the invisibility should end for that follower.

Invisibility should support:

- Raids
- Reconnaissance

The Shaman should not become permanently invisible through this spell unless a later upgrade explicitly allows it.

## MAGICAL SHIELD

Suggested project values:

- Range: 30
- Mana cost: 30
- Area: Small-to-medium
- Duration: 25 seconds
- Unlock tier: Early game

Function:

Magical Shield protects friendly followers from direct spell targeting and greatly reduces incoming damage.

Rules:

- Directly targeted offensive spells should bounce away or fail.
- Area-of-effect spells can still affect shielded followers if the spell is cast nearby.
- Shielded followers remain vulnerable to environmental hazards.
- Shielded followers die when entering lethal swamp terrain.
- Angel of Death can still kill shielded followers.
- Shielded followers should display a clear visual effect.
- The shield should not protect buildings unless explicitly configured.

Magical Shield should be especially useful for:

- Warriors
- Fire Warriors
- Preachers
- Raiding parties
- Followers defending the Shaman

## TORNADO

Suggested project values:

- Range: 30
- Mana cost: 35
- Area: Medium
- Duration: 20–30 seconds
- Unlock tier: Mid game

Function:

Tornado creates a moving environmental hazard.

Behavior:

1. Tornado appears at the cast location.
2. It remains briefly in place.
3. It moves in a controlled random direction.
4. It pulls nearby followers and loose objects toward it.
5. It launches affected targets in random directions.

## SWAMP

Suggested project values:

- Range: 30
- Mana cost: 50
- Area: Medium
- Duration: Until 10 follower deaths or map-configured expiration
- Unlock tier: Mid-to-late game

Function:

Swamp creates a lethal terrain hazard.

Any follower entering the swamp should die immediately unless protected by a future explicitly configured exception.

Rules:

- The Shaman is immune.
- Shielded followers still die.
- Angel of Death remains unaffected by the swamp’s follower limit.
- The swamp disappears after killing 10 followers by default.
- The kill limit must be configurable.
- The swamp should be clearly visible and readable.
- Buildings placed in the swamp should be handled according to the terrain system’s building rules.

Swamp should be useful for:

- Defending settlements
- Blocking narrow routes
- Protecting strategic locations
- Destroying large enemy groups
- Controlling access to reincarnation circles

# 12. SUPER SPELLS

Super spells require no mana, but they are not part of the normal repeatable spellbook.

They are obtained as one-shot charges from worshipping Stone Heads in specific maps or special locations.

Each super spell should have:

- One-shot charge count
- Map or Stone Head unlock condition
- Unique visual presentation
- Save-game persistence
- Clear confirmation before casting
- A powerful but understandable effect

## ARMAGEDDON

Suggested project values:

- Range: 100
- Mana cost: None
- Charges: One-shot
- Availability: Special Middle Ground and Head Hunter-style maps or equivalent late-campaign locations

Function:

Armageddon creates a massive arena at the target location.

All followers in the world are teleported to the arena and forced into a large battle.

Rules:

- Shamans are placed on elevated sections.
- Shamans receive permanent protective shields.
- Shamans cannot directly damage one another during the battle.
- Followers fight until only one tribe’s followers remain.
- When a Shaman has no followers left, that Shaman’s shield disappears.
- Another Shaman executes the defeated Shaman with lightning.
- The last surviving tribe wins the level.

Implementation requirements:

- Pause or safely suspend ordinary world simulation during the transition.
- Preserve follower ownership.
- Prevent followers from being permanently lost if the event is interrupted.
- Provide a clear pre-cast warning.
- Support deterministic resolution where practical.
- Make the event compatible with victory and defeat states.

# 16. SPELL BALANCE PRINCIPLES

Balance spells around meaningful choices rather than raw damage.

Every spell should have:

- A clear purpose
- A clear counterplay option
- A meaningful cost or restriction
- A readable visual effect
- A reason to use it instead of another spell

Avoid making high-cost spells universally superior.

Examples:

- Blast is cheap and disruptive.
- Lightning is precise and lethal.
- Swarm is disruptive but not destructive.
- Magical Shield protects against direct spells but not area effects.
- Land Bridge changes access rather than dealing damage.
- Swamp controls routes but has limited kills.
- Firestorm destroys groups and buildings but risks friendly casualties.
- Volcano permanently changes the battlefield but is expensive.
- Super spells are powerful because they are rare, not because they are repeatable.

### PHASE 1 TECHNOLOGY STACK

Build Phase 1 in Unreal Engine 5.4 or later, using the following stack:

- Engine: Unreal Engine 5
- Primary language: C++
- Visual scripting: Blueprints only for composition, tuning, UI flow, and rapid prototyping; do not place core simulation logic exclusively in Blueprints
- Build system: Unreal Build Tool
- IDE: Visual Studio 2022 on Windows, with Rider as an optional alternative
- Source control: Git with Git LFS for large binary assets
- Input: Enhanced Input
- Gameplay framework: Actor Components, Data Assets, Gameplay Tags, Interfaces, and Subsystems
- Data configuration: Primary Data Assets and Data Tables where appropriate
- AI navigation: Unreal Navigation System with NavMesh; use StateTree or Behavior Trees only where they simplify the prototype
- Physics and ragdoll: Chaos Physics and Physical Animation/Ragdoll systems
- Terrain: Landscape for the Phase 1 world; do not implement runtime terrain deformation yet
- Procedural generation: C++ world-generation subsystem using deterministic seeded noise and controlled placement rules
- Rendering: Nanite and Lumen only where they provide clear value; maintain a scalable fallback for prototype performance
- UI: UMG
- Audio: MetaSounds or standard Unreal audio assets, whichever is faster to iterate
- Testing: Unreal Automation Tests for deterministic generation and core gameplay rules, plus repeatable in-editor playtests
- Profiling: Unreal Insights, stat commands, and built-in profiling tools

### PHASE 1 ARCHITECTURE

Keep these modules lightweight. If separate Unreal modules would create unnecessary setup overhead, preserve the same boundaries as folders, namespaces, and clearly separated classes.

### PHASE 1 IMPLEMENTATION RULES

- Use C++ for authoritative gameplay rules and reusable systems.
- Use Blueprint child classes for asset assignment, animation setup, VFX, sound, and designer-facing tuning.
- Represent TAKA as a data-driven spell asset rather than a special-case method on the Shaman.
- Represent House, Campfire, and Reincarnation Circle as data-driven building definitions using the same building framework.
- Use interfaces for damage receivers, interactables, spell targets, and tribe-owned entities.
- Use Gameplay Tags for factions, damage types, unit states, and interaction categories.
- Use deterministic seeds for terrain, resource placement, and enemy placement.
- Keep the initial world small enough to profile easily.
- Use simple capsule or character collision for ordinary movement and Chaos ragdolls only during knockdown or launch states.
- Use object pooling only where profiling shows repeated allocation is a problem.
- Do not introduce Mass Entity, World Partition, or a custom ECS during Phase 1 unless profiling proves the simpler Actor-based approach inadequate.
- Keep all balance values editable through Data Assets or Data Tables.
- Add debug visualization for spawn points, resource locations, navigation, spell traces, damage impulses, and reincarnation state.
- Preserve the existing TAKA implementation and data asset unless a compatibility change is required.
- Do not rebalance TAKA without reporting the change first.
- Add automated tests for spell range, mana cost, target filtering, and friendly-fire behavior.

# 20. ENGINEERING RULES FOR CLAUDE

When implementing a feature:

1. Explain the architecture briefly.
2. Identify dependencies and compatibility risks.
3. Preserve existing working behavior unless a change is required.
4. Implement the smallest functional version.
5. Add or update data assets and configuration values.
6. Add automated tests for core rules.
7. Test the feature in the editor.
8. Fix errors.
9. Do not prematurely add polish.
10. Do not rewrite working systems unnecessarily.
11. Keep systems modular.
12. Keep balance values configurable.
13. Document important interfaces.
14. Maintain backward compatibility when practical.
15. Report any balance changes to existing spells.
16. Stop after the requested milestone and report results.

When a feature depends on another unfinished system:

Create an interface or stub rather than blocking the entire project.

# 21. IMPORTANT DEVELOPMENT PRINCIPLE

DO NOT BUILD “FEATURES.”

BUILD SYSTEMS.

For example:

Do not create:

“Fireball code.”

Create:

SPELL SYSTEM
→ TAKA — Blast is one implementation.

Do not create:

“Lightning code.”

Create:

SPELL SYSTEM
→ Lightning is one data-driven implementation using shared damage, targeting, knockback, ignition, and building-interaction systems.

Do not create:

“Warrior AI.”

Create:

UNIT SYSTEM
→ Warrior is one unit definition.

Do not create:

“House code.”

Create:

BUILDING SYSTEM
→ House is one building definition.

Do not create:

“Enemy tribe code.”

Create:

TRIBE SYSTEM
→ Player tribe and enemy tribes use the same underlying framework wherever practical.

Do not create:

“Swamp terrain code.”

Create:

TERRAIN HAZARD SYSTEM
→ Swamp, lava, fire, and future hazards use shared interfaces and state rules.

This will dramatically reduce development complexity.
